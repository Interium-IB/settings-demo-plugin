# Тестовые плагины настроек

Семь отдельных нативных плагинов без сетевых запросов и хуков:

- `settings_demo_switch` — два переключателя с разными начальными состояниями.
- `settings_demo_checkbox` — два независимых чекбокса.
- `settings_demo_text` — однострочный и многострочный текст, кириллица и лимиты UTF-8.
- `settings_demo_select` — выпадающий список из трёх вариантов.
- `settings_demo_radio` — три радиокнопки с единственным выбором.
- `settings_demo_slider` — два ползунка с шагом, один с отрицательными значениями.
- `settings_demo_all` — все шесть типов, всего десять полей в одном окне.

Каждый `settings_demo_*.zig` — отдельная библиотека со своим именем и хранилищем. `fields.zig` содержит типизированные секции `kit.Section`, `demo.zig` — общий код экспортов и чтения настроек. Общий плагин собирает секции через `kit.Spec`; JSON создаётся SDK при компиляции, вручную его писать не нужно. Плагины демонстрируют элементы формы: галочки и прочие поля не меняют поведение Telegram или самого клиента. Значения не пишутся в логи. Полный синтаксис — в [руководстве Zig DSL](../../include/SETTINGS_DSL.md).

## Сборка

Из корня репозитория, PowerShell и установленный Zig 0.17.0:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/build-settings-demo-plugins.ps1
```

Готовые Windows x64 DLL появятся непосредственно в `dist/settings_demo_*.dll`. Временные результаты компиляции — `build/settings-demo-plugins/windows/`. Скрипт не запускает клиент и не устанавливает плагины автоматически. Остальные файлы `dist/`, включая `dist/data`, сохраняются.

Для Linux x86_64 можно собрать SO тем же скриптом с `-Target linux` (в том числе кросс-компиляцией); на Linux с Zig отдельный плагин также собирается напрямую:

```bash
mkdir -p dist
zig build-lib -dynamic -O ReleaseSmall -target x86_64-linux-gnu --dep mandagram -Mroot=src/native/examples/settings-demo/settings_demo_all.zig -Mmandagram=src/native/include/mandagram_plugin.zig -femit-bin=dist/settings_demo_all.so
```

## Ручная проверка

1. Используйте клиент, собранный из `dev` с поддержкой `checkbox`, `radio`, `slider`. Более старый клиент пропустит неизвестные поля.
2. Скопируйте нужные DLL/SO в `<portableDir>/plugins/`. Для отдельной проверки возьмите новый portable root без настоящих сессий. Не переименовывайте файлы: их имена используются в `get_setting`.
3. Откройте «Настройки → Плагины», включите нужный плагин и нажмите шестерёнку. Откроется страница с секциями и стрелкой назад. Для проверки всего набора достаточно `settings_demo_all`.
4. Измените поля: значения сохраняются автоматически в фоне. Вернитесь стрелкой назад, повторно откройте настройки, затем отключите/включите плагин: значения должны сохраниться. Если запись не удалась, изменения остаются на экране и доступны для повторного сохранения.

Значения принадлежат клиенту и хранятся через `AppPaths` в `<portableDir>/data/plugins/<имя плагина>/settings.properties`. Даже если ключи у отдельных плагинов и общего примера совпадают, их значения независимы.

## Проверка нативного API

После сборки Windows DLL:

```powershell
.\gradlew.bat test --tests com.mandagram.plugin.PluginSettingsDemoTest -PpluginDemoDir=dist
```

На Linux после сборки SO используйте `./gradlew` с теми же аргументами. Без `pluginDemoDir` этот отдельный native-тест пропускается; при заданном каталоге отсутствие любой из семи библиотек считается ошибкой.

Тест загружает все семь настоящих библиотек через `PluginBridge` в изолированном portable root Gradle, проверяет metadata и схемы, начальные значения в `init`, кавычки/переносы строк/обратные слеши, чтение изменённых значений без перезагрузки, отказ в записи неверного значения и сохранность после выгрузки/повторной загрузки. Для чтения используется дополнительный диагностический экспорт примеров `mandagram_demo_read_setting`, который через DSL при каждом вызове обращается к `PluginApi.get_setting`; отдельного кеша значений в плагинах нет. Это не проверка UI или авторизованного Telegram.
